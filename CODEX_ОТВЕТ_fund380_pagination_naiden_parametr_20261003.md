# Codex: параметр пагинации дерева найден — это `page`, а не `nPage`

Дата: 2026-10-03. Отвечает на ваш блокер «запрос второй страницы возвращает повтор первой».
Разведка выполнена на живом сайте, 11 запросов с паузами 3–4 с.

## Причина

В `run_fund_opisi.py` (v2, строка ~313) номер страницы уходит в `nPage`, а `page` жёстко `"1"`:

```python
params = {"page": "1", "nPage": str(page), "id": "0", "parentId": object_id,
          "objectType": object_id + "-1050", "showPageList": "true", "completeWorkId": "-1"}
```

**Сервер `nPage` игнорирует.** Страницу задаёт `page`. Отсюда вечная первая страница
и 20 дел на опись при 37–134 страницах.

То же и в `frozen/.../searcher_rgia.py::_tree_params` — там `"page": "1", "nPage": str(page)`.
Для списка описей фонда это не вскрылось: описей 41, три страницы, и инвентарь собрался
(видимо, другим путём), а на делах дефект проявился в полный рост.

## Проверено на живом сайте (опись 21, `2841185`, tree index 202624)

| Запрос | `pageList` | id получено | Первый id | Вывод |
|---|---|---|---|---|
| `page=1` | `1,1,1,2,37` | 20 | 2447116488 | — |
| `page=2` | `1,1,2,3,37` | 20 | 2447116888 | **другая страница ✓** |
| `page=3` | `1,2,3,4,37` | 20 | 2447117288 | другая ✓ |
| `page=37` | `1,36,37,37,37` | **4** | 2447130788 | последняя, неполная ✓ |
| `page=38` | `1,37,38,37,37` | **0** | — | за пределом ✓ |

Что НЕ влияет (проверено, даёт повтор первой): `nPage`, `orderNumber`, `count`,
а также вариант с полным набором полей `_tree_params` при `id = <опись>` — он возвращает
**0 узлов** (для дел описи нужен именно `parentId` + `objectType`, как в v2).

## Рабочие параметры запроса дел описи

```python
params = {
    "page": str(page),            # ← ЕДИНСТВЕННОЕ изменение: номер страницы сюда
    "nPage": str(page),           # можно слать тем же числом, сервер его не читает
    "id": "0",
    "parentId": object_id,
    "objectType": object_id + "-1050",
    "showPageList": "true",
    "completeWorkId": "-1",
}
```
URL прежний: `GET /ajax/tree/{tree_index}`; `tree_index` берётся из `data-search-index`
на `/object/{opis_id}` и сессионен — перечитывать, как сейчас.

## Разбор `pageList` (первый узел ответа, `id: null`)

Формат `a,b,c,d,e`: **c — текущая страница, d — следующая, e — всего страниц**.
Признак выхода за предел: `c > e` и пустой список узлов (`page=38` → `1,37,38,37,37`, 0 id).
`_tree_page_count` уже читает `parts[4]` — это верно, менять не нужно.

## Что это даёт

Опись 21: 37 страниц × 20 = **~740 дел** вместо 20. По всем 41 описи — 1941 страница,
**~38 800 дел** вместо 727. Критерий полноты из брифа v3 (`pages_completed` ==
все страницы, накопление `object_ids`) теперь выполним.

Проверочный тест для пакета: `page=37` у описи 21 должен дать ровно 4 узла,
`page=38` — ноль; на первой странице 20. Это отличает рабочую пагинацию от повтора.
