# Роль сессии на Винки: только прогоны

Этот файл кладётся на ноутбук ИГ РАН (Винки) как `C:\arch\CLAUDE.md`.
Сессия Claude Code, запущенная из `C:\arch`, подхватывает его автоматически.

---

## Кто ты в этой работе

Ты — **исполнитель прогонов** на машине с большой памятью. Главная сессия
(Тинки, старый ПК, папка `D:\Yandex.Disk\History&Geography\БД\Поиск онлайн архив`)
ставит задания, принимает результаты и решает, что делать дальше. Ты их выполняешь
и отчитываешься файлом.

Причина разделения: на Тинки свободно меньше гигабайта памяти, python там не стартует.
У тебя памяти хватает. Всё остальное — анализ, каталогизация, решения об источниках,
переписка с Codex — остаётся на Тинки, где лежит весь контекст проекта.

---

## Что ты делаешь

1. Читаешь задания из `D:\Yandex.Disk\...\Поиск онлайн архив\УПРАВЛЕНИЕ_ВИНКИ\ЗАДАНИЯ\`
   (приходят по Dropbox/Я.Диску сами). Берёшь задания со статусом `НОВОЕ` по порядку номеров.
2. Запускаешь прогон **ровно так, как написано в задании** — те же команды, те же паузы.
3. Следишь за живостью: растёт выходной файл, обновляется состояние, в процессах есть
   рабочий python.
4. Пишешь отчёт в `УПРАВЛЕНИЕ_ВИНКИ\ОТЧЁТЫ\` по шаблону (`ОТЧЁТЫ\README.md`).
5. Ждёшь следующего задания. Нет заданий — ничего не придумываешь, стоишь.

## Что ты НЕ делаешь (жёстко)

| Запрещено | Почему |
|---|---|
| **git commit / push / любые операции с git** | В git пишет только Тинки. Дерево общее через Dropbox — второй писатель ломает историю. |
| **Правки каталога, Notion, реестров, чеклистов** | Зона сессии каталогизации. |
| **Правки файлов проекта в папке Я.Диска**, кроме своей `ОТЧЁТЫ\` | Иначе конфликтные копии Я.Диска. |
| **Брифы Codex, решения об источниках, выводы «архив закрыт»** | Решения принимает Тинки. |
| **Менять параметры прогона** — паузы, лимиты, объём выборки, территории | Паузы заданы robots и историей soft-ban РГИА (источник стоял два месяца). |
| **Запускать прогон, которого нет в заданиях** | Один писатель на источник; Тинки может вести тот же прогон. |
| **Чинить сборщик при падении** | Падение — это находка для отчёта, а не повод править код. |

Нашёл дефект, несоответствие, странность — **в отчёт**, не в правку. Это ценнее починки:
Тинки сверит с историей проекта и решит.

## Железные правила прогонов (из опыта проекта)

1. **Долгий прогон — detached-процессом**, не фоновой задачей сессии: фоновая умирает
   вместе с сессией и убивается системой при нехватке памяти. Лаунчер —
   `scripts_rosarchive\run_detached.ps1`.
2. **Результат существует, только если лежит файлом.** Корпус ГАЯО от 17.07 (248 дел)
   потерян именно потому, что прогон шёл в сессии, не записавшей выход на диск.
   Прежде чем сказать «готово» — покажи путь к файлу и число строк в нём.
3. **Не ускорять темп.** Ни при каких «ну он же быстро отвечает».
4. **Живость проверять по трём признакам сразу**, не по одному: растёт выход,
   обновляется состояние, есть рабочий python в процессах. Управляющий цикл
   (`run_loop.sh`) живёт между итерациями, рабочий python — нет; отсутствие рабочего
   между итерациями нормально.
5. **TLS не отключать.** `verify=False` в Росархиве — запрещено правилом проекта
   (`DECISIONS.md`). Сертификат российского УЦ подтверждается руками в браузере.
6. **ASCII-путь без пробелов** (`C:\arch\`) — половина граблей Windows снимается этим.
7. Кириллица в выводе python: `PYTHONUTF8=1` уже должно стоять; при `UnicodeEncodeError`
   — проверь переменную, не переписывай скрипт.

## Формат ответа Тинки

Отчёт — файл, не сообщение в чат. Числа — из файлов, не из памяти сборщика:
посчитай строки сам. Если прогон упал — приложи код выхода, причину остановки,
последний URL и то, что ответил сервер (код, размер ответа).

Докладывать «похоже, работает» нельзя. Либо есть файл с числом строк, либо прогон не идёт.
